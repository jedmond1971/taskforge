# Data integrity invariants (A2 audit)

- **Issue key generation is atomic but not tie-safe** — `createIssue` in `actions.ts` uses `SELECT ... FOR UPDATE` on the Project row inside a Prisma transaction to serialise concurrent inserts (the `generateIssueKeyWithRetry` retry loop has been replaced; `src/lib/issue-keys.ts` is now unused by the main flow), but the next-key logic itself is `findFirst({ orderBy: { createdAt: "desc" } })` → parse the numeric suffix → `+1`. This assumes the row with the latest `createdAt` also has the highest key number. **That assumption breaks on `createdAt` ties** — e.g. `prisma/seed.ts` creates each project's issues via `Promise.all([...prisma.issue.create(...)])`, so several rows can land in the same DB tick with equal or near-equal `createdAt` values, and Postgres doesn't guarantee tie-break order matches insertion/key order. Confirmed reproducible: creating a new issue via the UI on a freshly-seeded `PL` project can pick a stale row as "last", compute an already-used key, and 500 with `Unique constraint failed on the fields: (key)`. Not yet filed as a JFR issue. Workaround for testing: insert fixture issues directly via SQL with explicit, strictly-increasing `createdAt` values instead of going through `createIssue`/the UI. A real fix would sort by the numeric key suffix (or a monotonic sequence) rather than `createdAt`.
- **Kanban position writes are transactional** — `moveIssue` runs a single `prisma.$transaction` that locks the project row, reindexes both affected columns, and updates the issue `statusId` atomically. `reorderIssues` is also wrapped in a transaction. Position write failures throw an error (client retries). The DEFERRABLE unique constraint is on `(projectId, statusId, position)`.
- **Any `statusId` change must also set `position`** — the DEFERRABLE constraint means a write that changes `statusId` without updating `position` will violate the constraint if another issue in the destination column already holds that position. The safe pattern: `count({ where: { projectId, statusId: newStatusId, id: { not: issueId } } })` gives the append-to-end position. For bulk moves, count excluding all moving ids and assign `basePosition + i`. This applies to every code path that writes `statusId`, not just drag-and-drop.
- **S3 orphan cleanup on delete** — `DELETE /api/issues/[issueId]` fetches all attachments and deletes their S3 objects before cascading the DB delete. `DELETE /api/docs/[projectKey]/sections/[sectionId]` does the same for DOCUMENT-type pages. `deleteProject` (`src/app/(dashboard)/projects/[projectKey]/actions.ts`) also fetches and deletes all attachment and DOCUMENT-page S3 objects before the Prisma delete.
- **PageRevision cap = 50** — see `.context-docs/docs-invariants.md` invariant #6.
- **Notification cap = 100** — `src/lib/notifications.ts` prunes the oldest notifications beyond 100 after every insert. See `.context-docs/notifications.md`.
- **ActivityLog.userId is nullable** — `SET NULL` on user delete preserves audit history. `issueId` still cascades on issue delete.
- **SavedFilter requires projectId** — filters are project-scoped to prevent cross-tenant data leaks. `getMyFilters(projectId)` and `saveFilter(..., projectId)` require a projectId. The global `/search` page cannot save/load filters; use the project-specific search panel for that.
- **The v1 API does not follow the transactional/locked position-write pattern above, and can 500 on a position collision (JFR-122, open)** — `POST /api/v1/issues` (`src/app/api/v1/issues/route.ts`) and `PATCH /api/v1/issues/[key]` (`src/app/api/v1/issues/[key]/route.ts` ~line 97) both do a plain, non-transactional `prisma.issue.count({ where: { projectId, statusId } })` (POST's version isn't even scoped to `statusId` — it's a project-wide count) to compute the new `position`, then a separate `create`/`update`. The `count()`-as-position trick from the "safe pattern" bullet above only works if positions within a status column stay contiguous (`0..n-1`) — it silently breaks once a column has a gap (from a deleted row, a manual reorder, or any other write path that doesn't renumber on the way out), because `count()` can then equal an *existing* row's position instead of one past the end. Confirmed twice: JFR's "Backlog" column via POST (2026-07-31) and JFR's "Done" column via PATCH (2026-08-11, moving JFR-116 to Done). POST's retry loop makes this worse by treating the resulting P2002 as a key collision and retrying with a new key but the same broken position, so it fails 5x identically and surfaces a misleading "Could not generate unique issue key". Real fix is likely `MAX(position) + 1` scoped to `(projectId, statusId)` instead of `COUNT(*)`, in both routes.
- **`moveIssue`/`reorderIssues` support an optional trailing `sprintScopeId` param (JFR-105)** — a Sprint-mode board only shows the active sprint's issues client-side, but the `(projectId, statusId, position)` column on disk also contains backlog/other-sprint issues invisible to that client. Passing `sprintScopeId` makes both functions treat the incoming index/order as relative to the *visible* (matching-`sprintId`) subset only, and map it back onto the correct absolute slots in the full column — hidden issues' relative order is preserved, never reordered, though their raw position integers can still shift when the column is reindexed after a move. `sprintScopeId` omitted (`undefined`) is the exact legacy behavior — every existing Kanban-mode call site is unaffected. Don't copy this pattern for a new filtered-view feature without first checking whether the underlying `(projectId, statusId, position)` sequence is genuinely shared across the hidden/visible split, the way sprint and backlog issues share a status column.
- **"At most one X in state Y" invariants belong in the DB, not just app code** — JFR-105's "one ACTIVE sprint per project" is enforced by a hand-added, **non-deferrable** partial unique index (`CREATE UNIQUE INDEX ... ON "Sprint"("projectId") WHERE status = 'ACTIVE'`), not expressible via `@@unique` in Prisma. Non-deferrable is correct whenever the write is a single-row `UPDATE` (not a multi-row reindex needing a transient-duplicate window) — contrast with the DEFERRABLE `(projectId, statusId, position)` constraint above, which genuinely needs deferral because `moveIssue`/`reorderIssues` write a whole column's positions one row at a time. The server action still does an app-level pre-check first (for a clean user-facing error) and catches the resulting `P2002` as the real race guard — see `startSprint` in `sprint-actions.ts`.
- **`DocPage.position` DOES have a DB-level unique constraint** (corrected 2026-08-12 — an earlier version of this note, and CLAUDE.md, said it didn't; that was wrong). Migration `20260601000000_position_uniqueness` added a `DEFERRABLE UNIQUE (sectionId, position)` constraint for sectioned pages, plus a **non-deferrable** partial unique index `(docSpaceId, position) WHERE sectionId IS NULL` for top-level pages. The docs-tree drag-and-drop feature (`docs-sidebar-layout.tsx`, JFR-129-adjacent) hits this directly: `PATCH /api/docs/[projectKey]/pages/[pageId]` does a single plain `prisma.docPage.update`, not wrapped in `$transaction` — so each PATCH is its own implicit transaction, and the DEFERRABLE check still fires at the end of *that one statement*. Writing a dragged page straight to an index another page in the destination list already occupies 409s ("Concurrent modification") with `Unique constraint failed on the fields: (sectionId,position)`. Confirmed by reproducing it via Playwright, then fixing it: since there's no batch/transactional endpoint (and none is planned — sequential single-row PATCHes are still the right call for this low-volume UI), the client renumbers the *entire* destination list through a large temporary offset (`position: 1_000_000 + i` for every row, awaited sequentially) before writing final `0..N-1` positions in a second pass — mirrors the two-phase dedup trick the migration itself used, just done client-side per-drag instead of once at migration time. See `persistListOrder` in `docs-sidebar-layout.tsx`.
