# Local dev environment tooling notes (Windows / Jed's machine)

- **V1_API_KEY ends in `=` — use `cut -d= -f2-` to extract it** — the key is a base64 string (e.g., `...h9E1mESb0tU=`). `grep V1_API_KEY .env | cut -d= -f2` silently drops the trailing `=`, causing "Unauthorized" on every API call. Always use `cut -d= -f2-` (field 2 to end-of-line) or hardcode the value in Python scripts.
- **PowerShell git commit heredocs** — the bash `$(cat <<'EOF'…EOF)` pattern fails in PowerShell. Use the PowerShell here-string syntax instead: `git commit -m @'` … `'@` (closing `'@` must be at column 0).
- **Railway CLI is unusable in this environment** — every command (`whoami`, `status`, `variables`) produces no output and exits 1, even with `RAILWAY_API_TOKEN` set. Use the **Railway GraphQL API** instead: `POST https://backboard.railway.com/graphql/v2` with header `Authorization: Bearer $RAILWAY_API_TOKEN`. The token is exported in `~/.bashrc` (non-interactive shells may not source it — read it from the file directly). TaskForge production lives in project "striking-strength" (`7a369174-b77d-49c0-9ef0-f651541fe383`), environment `816d8546-3458-4855-9699-b77c855019b9`, service `taskforge` (`63950f57-c892-45d6-8c9e-937e75517994`), service `Postgres` (`a303a6b4-af40-457d-a017-08bfcf3647ff`).
- **Railway GraphQL API requires a browser-like `User-Agent` header** — requests with a bare/default `User-Agent` (e.g. Python `urllib`'s default) get a `403` with body `error code: 1010`, which is Cloudflare's bot-fight mode in front of `backboard.railway.com`, not an auth failure. This looks exactly like an expired/rotated token — before assuming the token is bad, retry with e.g. `User-Agent: Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/120.0 Safari/537.36`.
- **Restarting a crashed Railway service:** use the `serviceInstanceRedeploy` mutation — `mutation { serviceInstanceRedeploy(environmentId: "...", serviceId: "...") }`.
- **Setting a Railway env var:** use the `variableUpsert` mutation — `mutation VariableUpsert($input: VariableUpsertInput!) { variableUpsert(input: $input) }` with `input: { projectId, environmentId, serviceId, name, value }`. Returns a bare `true` on success. Setting a variable this way redeploys the service automatically (same as editing it in the dashboard) — used to set `AI_CHAT_ENABLED=true` on the taskforge service during the AI Chat work.
- **`taskforge-db` Docker container may not exist at all** (found 2026-08-06) — `docker ps -a --filter name=taskforge-db` returned nothing, not even a stopped container; `docker start taskforge-db` in the startup checklist fails silently in this case rather than erroring. Recovery: `docker run -d --name taskforge-db -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=taskforge -p 5433:5432 postgres:16` (the `postgres:16` image was already pulled locally), then `npx prisma migrate deploy` to replay the full existing migration history non-interactively (unlike `migrate dev`, this works fine in Claude Code's shell against an empty DB), then `npm run db:seed`.
- **Manually triggering a Railway deploy for a specific commit** — `serviceInstanceDeploy(serviceId, environmentId)` with no other args redeploys whatever commit Railway last deployed, **not** the actual latest commit on the branch (confirmed 2026-08-06: it silently redeployed a two-commits-old build while auto-deploy-on-push was off). Pass `commitSha` explicitly (full 40-char SHA from `git rev-parse <ref>`) to deploy a specific commit. Verify which commit is actually building via `deployments(input: {serviceId, environmentId}, first: N) { edges { node { status meta } } }` and check `meta.commitHash`/`meta.commitMessage` — don't assume the trigger call deployed what you intended.
- **Direct production DB access:** query the GraphQL `variables(projectId, environmentId, serviceId)` field for the Postgres service and use its `DATABASE_PUBLIC_URL` with local `psql`. Fetch it fresh each time; never write it to a file that survives the session or commit it. The `variables` field returns a **flat key/value object** (not edges/nodes) — query it as `{ variables(projectId: "...", environmentId: "...", serviceId: "...") }` with no subfields and access results as `d['data']['variables']['KEY_NAME']`. Queries with `{ edges { node { name value } } }` subfields fail with a schema validation error.
- **Seeded users' org membership (fixed 2026-08-06, JFR-102 session)** — `prisma/seed.ts` used to only create an `OrgMember` row for Alice when creating her workspace org; `member`/`carol`/`dave` got `ProjectMember` rows in her projects but had **no** `OrgMember` row at all (not even a separate personal org — that earlier note was wrong). This silently broke anything depending on `OrgMember` for those three (Group membership, org invites, org-level settings) and violated the tenancy invariant `addProjectMember` enforces at the app layer. Now fixed: the seed script gives all three a `MEMBER`-role `OrgMember` row in Alice's workspace org too. If you're on a DB seeded before this fix, re-run `npm run db:seed` to pick it up (org IDs are regenerated fresh each seed run, so don't hardcode one from a prior session).
- Auth page logos: `public/logo-light.png` and `public/logo-dark.png` are both **1254×1254 square** images. They are displayed at `w-[200px] sm:w-[260px]` on the login page — do not increase this without checking total page height fits inside a 1080p viewport (logo + card + gaps must stay under ~940px).
- **Favicon/icon assets use `.png`, not `.svg`** — `src/app/icon.png`, `public/icons/light/icon.png`, and `public/icons/dark/icon.png` replaced the old hand-crafted `icon.svg` files. Next.js App Router picks up `src/app/icon.png` natively (appears as `/icon.png` route in `next build` output). Do not add `icon.svg` back.
- **`public/icons/{light,dark}/icon-128.png`** are pre-cropped 128×128 square "JF" glyph marks (same family as the favicons, between the tiny `favicon-*.png` and the huge `icon-1024.png`). Reuse these for any compact UI that needs a small brand mark instead of the full wordmark (e.g. the collapsed sidebar rail in `Sidebar.tsx`, JFR-101) rather than generating a new asset.
- **Favicon glyph crop box** — to regenerate the icon set from the source logos, crop `(left=335, top=250, right=975, bottom=714)` from either 1254×1254 logo PNG to isolate the "JF" ribbon glyph (640×464px). Center on a 740×740 square canvas, filling with the corner-sampled background color (near-white for light, near-black `#0b0a0e` for dark). Downsample with Lanczos (`Image.LANCZOS` in Pillow). ICO files embed 16×16, 32×32, and 48×48.
- Playwright v1.59.1 is installed in `node_modules` only (not global). In CJS scripts: `require('/home/jamie/Projects/TaskForge/node_modules/playwright')`. **`npx playwright install chromium` requires sudo and will fail** — instead use `executablePath: '/usr/bin/google-chrome'` in `chromium.launch()`. `tmux` is not available — start the dev server in the background with `nohup`: `nohup npm run dev > /tmp/nextdev.log 2>&1 &` then `sleep 12` before driving it. Plain `npm run dev > /tmp/nextdev.log 2>&1 &` (without `nohup`) exits with code 144 in this environment. **Port 3000 may already be in use** (e.g. a leftover dev server from a prior session) — Next.js will silently fall back to 3001 or higher. Always resolve the actual port before writing Playwright URLs: `grep "Local:" /tmp/nextdev.log | head -1`.
- **No TypeScript `as X` casts in `.js` Playwright scripts** — `(el as HTMLInputElement).checked` causes `SyntaxError` in Node.js CJS. Write plain `el.checked` directly instead.
- **Calling Next.js server actions directly (bypass UI) for validation testing** — intercept the action ID at runtime via `page.on('request', req => { const h = req.headers()['next-action']; if (h) console.log(h, req.postData()) })`, then call it from inside `page.evaluate()`: `fetch(pageUrl, { method: 'POST', headers: { 'Next-Action': id, 'Content-Type': 'text/plain;charset=UTF-8' }, body: JSON.stringify([arg1, arg2, ...]) })`. The JSON array maps positionally to the action's parameters. Action IDs are build-time hashes — find them at runtime, don't hardcode. Useful for passing values that browser input validation would normally block (e.g. non-numeric strings to a `type="number"` field).
- **psql double-quoted identifiers in Node.js `execSync`** — `execSync('psql ... -c "SELECT \\"col\\" FROM \\"Table\\"')` loses the inner double quotes, causing `ERROR: relation does not exist`. Pass SQL via stdin instead: `execSync('psql postgresql://...', { input: 'SELECT "col" FROM "Table";', encoding: 'utf8' })`. This preserves all quoting.
- **Playwright + Next.js App Router client-side navigation** — after clicking a link that triggers client-side routing, `page.url()` and `waitForLoadState('networkidle')` are unreliable. Use `page.goto('http://localhost:3000/projects/PL/issues/PL-1')` directly instead of clicking through from a list page.
- **Playwright `waitForURL` with glob patterns** — `page.waitForURL('http://localhost:3000/**')` resolves immediately if the page is already at a matching URL (e.g., you're already on `/login`). When waiting for login to complete, use a predicate instead: `page.waitForURL(url => !url.toString().includes('/login'), { timeout: 15000 })`.
- **Playwright `page.$('text=...')` with special characters** — the middle-dot `·` and similar Unicode characters can silently fail to match. Use `(await page.content()).includes('...')` for reliable substring checks.
- **`window.scrollBy`/`window.scrollTo` are no-ops in this app for Playwright scroll tests** — `DashboardShell.tsx`'s outer wrapper is `h-screen overflow-hidden`; the actual scrollable region is `<main className="overflow-y-auto">`. Scrolling the window does nothing and silently gives a false "stable/unchanged" reading for any before/after comparison. Scroll the real container: `document.querySelector('main').scrollBy(0, n)` or set `.scrollTop` directly. Found while verifying JFR-112/113 — an earlier "sticky panel doesn't move on scroll" check passed only because `window.scrollBy` never actually scrolled anything.
- **When verifying a viewport-constrained/sticky element, explicitly check its bounding rect against the viewport height** (`rect.bottom <= viewportHeight`), not just that the rect is stable across a scroll action. JFR-113 was a bug (chat panel input pushed below the fold) that existed undetected through JFR-112's own verification pass, because that pass only checked scroll-stability, never whether the initial on-load rect fit inside the viewport.
- **Backgrounding the dev server with shell `nohup ... &; disown` does NOT survive across separate Bash tool calls in Claude Code** — the process gets torn down when the tool call that spawned it returns, regardless of `nohup`/`disown`. A server started this way is already dead by the next tool call, producing confusing `ERR_TOO_MANY_REDIRECTS`/connection-refused symptoms that look like an app bug. Use the Bash tool's own `run_in_background: true` parameter instead (`npm run dev` with that flag) — that process is tracked by the harness and survives between calls. The `nohup`/exit-144 guidance above is superseded by this for any multi-step Playwright session.
- **Nested worktree tooling conflicts** — a git worktree created *inside* the repo tree (e.g. under `.claude/worktrees/<name>/`) breaks two tools for as long as it exists on disk, because neither is scoped to stop at the worktree boundary:
  - `npm run lint` / `next lint` fails with `Plugin "@next/next" was conflicted between ...` — ESLint walks up parent directories looking for `.eslintrc.json` (the repo's root config has no `"root": true`), finds the outer repo's copy in addition to the worktree's own, and errors on the duplicate plugin registration. Workaround inside the worktree: `npx eslint . --no-eslintrc -c .eslintrc.json --ext .ts,.tsx` (baseline: 0 errors, 10 pre-existing `@next/next/no-img-element` warnings). `npx tsc --noEmit` is unaffected.
  - `npm test` (vitest) run from the **main checkout** silently picks up and re-runs every `src/__tests__/*.test.ts` file a second time from inside the worktree path too (`vitest.config.ts` has no `exclude` for `.claude/worktrees/`), and the two parallel copies of the same Prisma-mock-based tests collide on shared mock state, producing flaky failures that look like a real regression. This is not a real test failure — remove or exit the worktree first, then re-run `npm test` from the main checkout to get a trustworthy result.
  - Git worktrees do **not** carry over `.env` (it's gitignored, so `git worktree add`/`EnterWorktree` gives you a working directory without it). Without it, `next dev` boots but NextAuth fails every request with `MissingSecret`, which manifests as an infinite redirect loop between `/` and `/login` — copy `.env` from the main checkout into the worktree before starting the dev server there.
- **Playwright `getByText('Alice Chen')` (or any seeded user's full name) is not unique** — it matches the sidebar account trigger *and* every avatar/comment-author mention rendered elsewhere on the page (10+ matches on a populated dashboard), throwing a strict-mode violation. Use `page.getByRole('button', { name: 'Alice Chen admin@taskforge.dev' })` to target the account dropdown trigger specifically (Playwright's error message on the failed `getByText` call conveniently lists the exact accessible name to use).
- **Verifying a production CSS/token-only deploy actually shipped, when the affected page just redirects (e.g. `/` → `/login`, so a 200-polling loop never fires)** — fetch the HTML (`curl -sL https://www.jedforge.com/login`), extract the `/_next/static/css/<hash>.css` link(s) (there are usually two — check both, per-route chunks vary in what they include), fetch that file, and grep it for a literal value you know is new (e.g. a distinctive OKLCH number). Far more reliable than polling for a status code on a route that already existed pre-deploy. Used to confirm JFR-103's new `--primary: oklch(55% .2 40.5)` was live.
