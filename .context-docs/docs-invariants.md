# Docs module invariants

The Docs module lives under `src/app/(dashboard)/projects/[projectKey]/docs/` (project view) and `src/app/(dashboard)/docs/` (global view). API routes are at `/api/docs/[projectKey]/...`.

**Rules enforced in code:**

1. **DocSpace is lazy-upserted** — there is no DocSpace creation endpoint. A `DocSpace` row is upserted automatically on any member's call to the docs API. The shared helper `resolveDocCtx` in `src/app/api/docs/_helpers.ts` handles this; all docs route files import it. The docs Next.js layout (`src/app/(dashboard)/projects/[projectKey]/docs/layout.tsx`) also upserts the DocSpace directly to fetch sidebar data — both upsert paths are intentional. Do not try to pre-create DocSpaces at project creation time.
2. **DocPageType** — two values: `NATIVE` (TipTap HTML stored in the `content` field — same format as issue descriptions/comments, not raw Markdown) and `DOCUMENT` (file upload; `fileKey`, `fileSize`, `mimeType` fields used instead). Do not add intermediate types without a product decision.
3. **`DocSpace.isPublic`** — when true, any authenticated JedForge user can read that project's docs even without a `ProjectMember` row. Only `PROJECT_LEAD` can toggle this via `PATCH /api/docs/[projectKey]` with `{ isPublic: boolean }`. `resolveDocCtx` returns `role: null` for non-member public readers; write operations (POST/PATCH/DELETE) still require a member role.
4. **Docs role enforcement** — enforced in all API routes via `resolveDocCtx` + permission helpers from `src/lib/permissions.ts`:
   - Read (GET): any project member, or any authenticated user on a public docspace
   - Create / edit pages and sections, file upload: `canEditIssues` (TEAM_MEMBER or PROJECT_LEAD)
   - Delete pages and sections: `canManageProject` (PROJECT_LEAD only)
   - Visibility toggle (`PATCH /api/docs/[projectKey]`): PROJECT_LEAD only (checked inline, not via `resolveDocCtx`)
5. **Docs search** — `GET /api/docs/[projectKey]/search?q=<query>` searches `DocPage.title` (all types) and `DocPage.content` (NATIVE only) with case-insensitive `contains`. Returns up to 20 results with `id`, `title`, `type`, `sectionTitle`, and a `snippet`. Accessible to any user who can read the docspace.
6. **Page revisions** — `PageRevision` rows are snapshot-only (created on save, never mutated). The PATCH handler for `/api/docs/[projectKey]/pages/[pageId]` automatically snapshots the previous content into a new `PageRevision` whenever `content` is included in the update body — do not break this side-effect when modifying that handler. Restoring a revision means writing its content back to `DocPage.content` and creating a new revision from the current content first (the auto-snapshot in PATCH handles this). **Cap: 50 revisions per page** — oldest are pruned in the same transaction as each content save.
7. **Issue↔DocPage cross-links** — `IssueDocLink` is the junction table (cascade-deletes when either side is deleted). Both issue and page must belong to the same project — enforced in the `linkDocPage` server action. Manage links via `linkDocPage` / `unlinkDocPage` in `actions.ts`; read linked issues for a page via `GET /api/docs/[projectKey]/pages/[pageId]/links`.
8. **DOCUMENT page file lifecycle** — files are uploaded via `POST /api/docs/[projectKey]/pages/[pageId]/file` (multipart `file` field; PDF and DOCX only, 50 MB max). That endpoint also sets `type = DOCUMENT` on the page, so posting a file to an existing NATIVE page converts it. `GET` on the same route returns `{ url, mimeType, fileName, html }` with a 1-hour presigned S3 URL (`html` is the cached/lazily-converted DOCX preview, see below). Files are stored at `docs/[docSpaceId]/[pageId]/[uuid]-[sanitized-filename]` in S3. The DELETE handler for a page removes the S3 object automatically; replacing a file via POST also deletes the previous object. PDFs render inline via `<iframe>`. **DOCX files render an in-app preview** (JFR-131, 2026-08-13): `.docx` (OOXML) is converted server-side via `mammoth` to sanitized HTML, cached on `DocPage.docxPreviewHtml`, and lazily converted+cached on first view for pages that predate the feature. Embedded images are extracted to S3 under `docs/[docSpaceId]/[pageId]/docx-images/` and served through the app's own proxy route (`/api/docs/[projectKey]/pages/[pageId]/images/[imageKey]`) rather than linked via presigned URL, since a presigned URL baked into cached HTML would go dead after an hour. Legacy `.doc` (pre-OOXML binary, mime `application/msword`) is **not** supported by mammoth and keeps the original download-only fallback. The UI creates the page stub first then uploads — a failed upload leaves an orphaned DOCUMENT page with no file (known edge case).
9. **Doc page delete UI** (JFR-132, 2026-08-13) — the `DELETE /api/docs/[projectKey]/pages/[pageId]` route (rule 4 above) existed for a long time with no UI ever calling it. The doc-detail page (`src/app/(dashboard)/projects/[projectKey]/docs/[pageId]/page.tsx`) now computes `canManageProject(role, grants)` and passes it as a `canDelete` prop to both `DocPageEditor` and `DocDocumentView`, mirroring the `canManage` pattern `docs/layout.tsx` already used for the visibility toggle. Neither view had a `canManage`/PROJECT_LEAD-level prop before this — if you add another PROJECT_LEAD-only action to either view, check whether `canDelete` can be reused/renamed rather than plumbing a third permission prop through the same page.
10. **Serving raw binary bytes from a Next.js route handler** — `new NextResponse(buffer, {...})` where `buffer` is a Node `Buffer` fails `tsc` (`Buffer<ArrayBufferLike>` is not assignable to `BodyInit`); wrap it as `new NextResponse(new Uint8Array(buffer), {...})`. No prior route in this codebase served binary bytes directly before the DOCX image proxy (rule 8, JFR-131) — every other file-serving route (`/api/avatar`, the docs file route) redirects to a presigned S3 URL instead. Also: `@aws-sdk/client-s3`'s `GetObjectCommand` throws an error with `.name === "NoSuchKey"` (not a special return value) when the key doesn't exist — catch that specifically to return a real 404, otherwise it falls through to a generic 500.
11. **`DocPage.status`** (JFR-133, 2026-08-17) — `DocPageStatus` enum (`DRAFT | IN_REVIEW | PUBLISHED`), defaults to `PUBLISHED`. This is a display-only signal, not an access-control gate — a `DRAFT` page remains visible to anyone who could already see it; only the pill differs. Editable via the same `PATCH /api/docs/[projectKey]/pages/[pageId]` route (rule 6) under the same `canEditIssues` permission as content edits — no separate endpoint. `DRAFT` was deliberately **not** made the default: backfilling existing rows as `PUBLISHED` avoids retroactively marking every pre-existing doc as unfinished.
12. **`DocPageView`** (JFR-133, 2026-08-17) — per-user "recently viewed" tracking, `@@unique([userId, pageId])` so each user has one row per page, upserted with a fresh `viewedAt` on every page open via `recordDocPageView()` (`src/lib/doc-page-views.ts`), called directly from the doc-detail Server Component (`docs/[pageId]/page.tsx`) rather than a REST endpoint — same "mutate during RSC render" precedent as the `DocSpace` lazy-upsert (rule 1). The docs list page queries the top 6 by `viewedAt desc`, scoped to the current project's `DocSpace`.
13. **Client-side TOC heading-id extraction has a React dev-mode gotcha** — `RichTextDisplay` (`src/components/ui/rich-text-display.tsx`) walks its `dangerouslySetInnerHTML` container for `<h2>` elements and assigns `id`s imperatively (the sanitizer's `ALLOWED_ATTR`, `src/lib/sanitize-html.ts`, doesn't include `id`, so this can't be done server-side without loosening that allowlist). A `useEffect` gated on `[content, onHeadingsExtracted]` is **not** enough: in dev mode, the very first `setState` call the effect makes back up to the parent (to report the extracted headings) triggers a subsequent re-render that resets this exact same DOM node's `innerHTML` back to its id-less form (confirmed via `sameNode === true` — it's not a remount, something clobbers the same node once). The effect now has **no dependency array** (reapplies ids after every commit) guarded by a signature ref so it only calls `onHeadingsExtracted` when the computed TOC actually changes — this makes id assignment self-healing regardless of the clobber. If you touch this effect, keep it dependency-array-free; adding `[content]` back reintroduces the bug.
