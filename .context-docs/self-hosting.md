# Self-hosting JedForge on Proxmox (runbook)

Why: stop paying for Railway for a while. The Railway deployment keeps working unchanged: everything here is opt-in by env var (`S3_PUBLIC_ENDPOINT`, `S3_FORCE_PATH_STYLE`, `TRUSTED_PROXY`), and `railway.toml` is untouched. Migration plan and decisions: `proxmox-migration-plan.md`.

## Layout

VM `jedforge-prod` (Proxmox VMID 120, Debian 13, 2 vCPU / 4 GB / 60 GB, `10.0.0.122`, `onboot`), user `jamie`, reached with the `id_ed25519_pve_claude` key. Everything lives under `/opt/jedforge`:

| Path | What |
|---|---|
| `repo/` | clone of this repo (public, no credentials) |
| `.env` | all config, mode 600, generated by `deploy/selfhost/bootstrap.sh` |
| `data/postgres`, `data/garage` | bind-mounted volumes |
| `backups/` | nightly `db/*.sql.gz` (14 days) + hard-linked `files/<date>/` snapshots |
| `.deployed-sha` | last commit the deploy timer put live |

Compose stack (`deploy/selfhost/docker-compose.yml`): `db` (Postgres 16), `garage` (S3-compatible store, initialised by `garage-init.sh`), `app` (built from the root `Dockerfile`), `cloudflared`. Ports are bound to `127.0.0.1`; the internet only reaches the box through the tunnel. UFW allows only SSH from the LAN.

## Things that differ from Railway (and why)

- **Two storage endpoints.** `RAILWAY_BUCKET_ENDPOINT=http://garage:3900` is what the server uses; `S3_PUBLIC_ENDPOINT=https://files.<domain>` is what presigned URLs are signed for (browsers can't reach `garage:3900`). Presigning is offline, so `src/lib/s3.ts` uses a second client only for `getSignedUrl`. Garage needs `S3_FORCE_PATH_STYLE=true` (no per-bucket DNS).
- **CSP.** `next.config.mjs` adds the `S3_PUBLIC_ENDPOINT` origin to `img-src` and `frame-src`. `headers()` is evaluated at **build** time for `next start`, so it is a Docker **build arg** (compose passes it); changing it needs `docker compose build app`, not just a restart.
- **Client IP.** `TRUSTED_PROXY=cloudflare` makes `clientIpFromHeaders` use `CF-Connecting-IP`. Cloudflare *appends* to a client-sent `X-Forwarded-For`, so the leftmost-XFF rule from `rate-limiting.md` (correct on Railway) would be spoofable here and let an attacker pick their own rate-limit bucket. Never set `TRUSTED_PROXY` on a host that is reachable without Cloudflare in front.
- **Migrations** run in `docker/entrypoint.sh` before `next start`, as `railway.toml`'s `preDeployCommand` does. A failing migration keeps the container unhealthy and `deploy.sh` rolls back to `jedforge-app:prev`.
- **Deploys** are pulled: `jedforge-deploy.timer` (5 min) runs `deploy.sh`, which deploys `origin/main` only when every check run on that SHA is green. Enabled only with `GO_LIVE=1`.
- **Cleanup cron** moved to `jedforge-cleanup.timer` (calls the endpoint on localhost). The GitHub workflow still points at Railway; delete it at cutover (it fails once Railway is gone).
- **Storage marker.** The orphan cleanup refuses to delete when the bucket marker and DB marker disagree (`storage-marker.ts`). Migrating copies the DB *and* the whole bucket (marker included) so they stay consistent; copying only one of them makes the first cleanup stop with a `409`.

## Bootstrap (idempotent)

```bash
# on the VM, as jamie; HANDOFF has CLOUDFLARE_TUNNEL_TOKEN, RESEND_API_KEY, ALERT_EMAIL_TO, ...
BRANCH=main bash /opt/jedforge/repo/deploy/selfhost/bootstrap.sh /path/to/handoff.env
cd /opt/jedforge/repo/deploy/selfhost && docker compose --env-file /opt/jedforge/.env up -d --build
```

Re-running never regenerates an existing secret (that would lock the database out). Missing values are listed at the end.

## Tunnel hostnames

The tunnel (`jedforge-prod`) is remotely managed, so public hostnames are set in the Cloudflare dashboard (Networking → Tunnels → jedforge-prod → Public Hostname): `www.jedforge.com` → `http://app:3000`, `files.jedforge.com` → `http://garage:3900`. Rehearse on throwaway names first (`stage.` / `stage-files.`) with `APP_ORIGIN` / `S3_PUBLIC_ENDPOINT` set to match.

## Day-to-day

```bash
docker compose --env-file /opt/jedforge/.env -f /opt/jedforge/repo/deploy/selfhost/docker-compose.yml logs -f app
systemctl list-timers 'jedforge-*'
journalctl -u jedforge-deploy -n 50
```

Restore: `gunzip -c backups/db/taskforge-<date>.sql.gz | docker exec -i jedforge-db-1 psql -U taskforge -d taskforge`, and `rclone sync backups/files/current GARAGE:jedforge` (same env-var remote as `backup.sh`); files deleted or overwritten in the last 14 days are under `backups/files-changed/<date>/`. The off-VM copy is the Proxmox `vzdump` job for VMID 120.

## Why Garage, not MinIO

The first design used MinIO. In November 2025 the project stopped publishing container images (Docker Hub and quay.io both refuse `pull`; source-only), so the stack uses Garage (`dxflrs/garage`, pinned). Garage differences that matter here: key ids must be `GK` + 24 hex and secrets 64 hex (`bootstrap.sh` generates that shape), path-style only, no shell in the image (so `garage-init.sh` runs `garage` via `docker exec`), CORS set through the S3 API, and metadata kept in sqlite for crash safety on a home server.
