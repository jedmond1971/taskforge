# Sprint workflow invariants (JFR-105)

1. **`Project.workflowMode`** is `KANBAN` (default) or `SPRINT`, set once at creation (`NewProjectDialog.tsx` mode selector → `POST /api/projects`) and never changed afterward — there is no UI, admin action, or API to switch an existing project's mode. Existing projects backfilled to `KANBAN` with no data migration.
2. **Sprint-mode-only UI**: the `Backlog` tab (`ProjectNav.tsx`) only renders when `workflowMode === "SPRINT"`. The Backlog page itself (`backlog/page.tsx`) redirects to `/board` if hit directly on a Kanban project (defense-in-depth for a stale bookmark).
3. **Board scoping**: on a Sprint-mode project, `board/page.tsx` queries issues filtered to the currently `ACTIVE` sprint's id only; with no active sprint it renders an empty state linking to the Backlog instead of `<KanbanBoard>`. Kanban-mode boards are completely unaffected — same query shape as before JFR-105.
4. **One active sprint per project, enforced at the DB level** — a partial unique index on `Sprint(projectId) WHERE status = 'ACTIVE'` (see `.context-docs/data-integrity.md`), not just app-side checking. `startSprint` in `sprint-actions.ts` still does an app-level pre-check for a clean error message, then catches the `P2002` from a lost race as the real guard.
5. **Any number of PLANNED sprints may exist; only one may be ACTIVE** (JFR-189, 2026-10-06) — `createSprint` no longer rejects a second open sprint. The Backlog page lists every open sprint (ACTIVE first, then planned by start date); backlog rows pick a target sprint from a native `<select>`. `startSprint`'s pre-check + the partial unique index remain the only guard, and the Start button is disabled while a sprint is active.
6. **Completing a sprint auto-unassigns non-Done issues** — `completeSprint` looks up the project's DONE-category `ProjectStatus` ids and `updateMany`s the sprint's issues where `statusId notIn` those ids to `sprintId: null`, inside one transaction with the `status: COMPLETED` write. The `ConfirmDialog` itemises the result (JFR-182): how many issues are Done and stay, how many aren't and return, and the returning ones listed (capped at 8, then "and N more"). The numbers come from `summarizeSprintCompletion` in `src/lib/sprint-completion.ts`, which shares `DONE_CATEGORY` with this query, and are read from the live sprint state (not a snapshot taken when the button was clicked); `sprint-completion.itest.ts` requires the preview and `completeSprint`'s real `movedToBacklogCount` to agree, including a renamed Done status and a project with no DONE status. The dialog is `destructive` only when something will actually move. `ConfirmDialog` gained optional `children` for this.
7. **Permissions**: `canManageSprint` (PROJECT_LEAD, or a Group-granted `SPRINT_MANAGE` permission) gates create/start/complete. Adding/removing issues to/from a sprint uses the existing `canEditIssues` (PROJECT_LEAD + TEAM_MEMBER, or `ISSUE_EDIT` grant) — it's routine issue editing, not a sprint-lifecycle action. Whenever a new `Permission` enum value is added, `GroupsSettings.tsx`'s `PROJECT_SCOPED_PERMISSIONS`/`ORG_SCOPED_PERMISSIONS` arrays and `PERMISSION_LABELS` map must be updated too — `PERMISSION_LABELS: Record<Permission, string>` is exhaustive, so `tsc` catches a missed one, but the two array lists are not type-checked and are easy to forget.
8. **`moveIssue`/`reorderIssues` sprint-scoping** — see `.context-docs/data-integrity.md`'s `sprintScopeId` bullet. Required for correctness, not optional: without it, dragging on a Sprint-scoped board (which only has the active sprint's issues in client state) would corrupt backlog issues' positions in the shared `(projectId, statusId, position)` column.
9. **Sprint dates are set at creation** (JFR-189) via `CreateSprintDialog`: duration 2w/3w/4w (10/15/20 business days, start day counted, Sat/Sun skipped — Wed the 1st → Tue the 14th) or Custom (free start/end). The server recomputes a preset's end date and rejects a weekend start for presets (`src/lib/sprint-dates.ts`). Dates are calendar days stored at UTC midnight — format with `timeZone: "UTC"`. `startSprint`/`completeSprint` keep a planned start/end and only fall back to "now" when null.
10. **New issues always land in the backlog** (`sprintId: null`) — the issue-creation form was not touched; assignment into a sprint happens only via the Backlog page's "Add to sprint" action.
11. **Editing and ordering (JFR-190)** — `updateSprint` edits name/goal/dates of any PLANNED or ACTIVE sprint (completed ones are refused); every field but the goal is required, same validator as create. `Sprint.position` is nullable: `null` everywhere means "never dragged" and `orderSprints()` (`src/lib/sprint-dates.ts`) shows active first then by start date; once `reorderSprints` has stored positions they rule, and `createSprint` appends new sprints to that order. `reorderSprints` rejects any id list that isn't exactly the project's open sprints and writes nothing.
12. **Auto-adjusting following sprints is opt-in and advisory** — when an edit changes start or end, the dialog (client-side `planFollowingShifts`) lists what would move and asks; the server recomputes the same shifts from its own open-sprint list when `adjustFollowing: true` (never trusts client-sent dates for other sprints). Each following sprint (display order, taken *before* the edit) starts the next business day after the previous ends and keeps its working-day length. Declining only saves the one sprint — nothing in the app requires sprints not to overlap. New-sprint dialog defaults come from `suggestNextSprint` (start = next business day after the latest-ending sprint, same length).
13. **Bulk "add to sprint" (JFR-180)** — `bulkUpdateIssueFields` takes `sprintId` (`null` = back to backlog); it throws on a Kanban project, a sprint from another project, or a `COMPLETED` sprint, and writes one `sprint` ActivityLog row per issue that actually changed. The Issues list shows the Sprint control only when `workflowMode === "SPRINT"` and the viewer can edit; it offers PLANNED/ACTIVE sprints plus "Backlog". Errors here are thrown, so in production a failed validation reaches the user as the generic Server Action message — the UI only offers valid choices, the throws are defence in depth.
14. **Backlog drag-and-drop into a sprint (JFR-181)** — `BacklogView` has one `DndContext` for two drag kinds, told apart by `data.type` (`"sprint"` reorder, `"issue"` backlog row). A sprint card is a `useSortable` droppable, so its id is the drop target for an issue; `disabled: { draggable: true }` (not `true`) keeps a card droppable when it can't be reordered (one sprint, or no `canManageSprint`). Issue drags use `pointerWithin` (falling back to `rectIntersection` for the keyboard) because `closestCenter` picks the wrong tall card; the keyboard path needs the custom coordinate getter in `BacklogView.tsx`, since `sortableKeyboardCoordinates` assumes the dragged item is sortable. Drop → `addIssueToSprint` (same `canEditIssues` gate as the "Add to sprint" select, which stays as the non-drag fallback); the sprints and backlog share one `useOptimistic` state (`src/lib/backlog-state.ts`) so rows and the per-section counts move at once. Dragging a row out of a sprint is not supported — use Remove.
