# Sprint workflow invariants (JFR-105)

1. **`Project.workflowMode`** is `KANBAN` (default) or `SPRINT`, set once at creation (`NewProjectDialog.tsx` mode selector → `POST /api/projects`) and never changed afterward — there is no UI, admin action, or API to switch an existing project's mode. Existing projects backfilled to `KANBAN` with no data migration.
2. **Sprint-mode-only UI**: the `Backlog` tab (`ProjectNav.tsx`) only renders when `workflowMode === "SPRINT"`. The Backlog page itself (`backlog/page.tsx`) redirects to `/board` if hit directly on a Kanban project (defense-in-depth for a stale bookmark).
3. **Board scoping**: on a Sprint-mode project, `board/page.tsx` queries issues filtered to the currently `ACTIVE` sprint's id only; with no active sprint it renders an empty state linking to the Backlog instead of `<KanbanBoard>`. Kanban-mode boards are completely unaffected — same query shape as before JFR-105.
4. **One active sprint per project, enforced at the DB level** — a partial unique index on `Sprint(projectId) WHERE status = 'ACTIVE'` (see `.context-docs/data-integrity.md`), not just app-side checking. `startSprint` in `sprint-actions.ts` still does an app-level pre-check for a clean error message, then catches the `P2002` from a lost race as the real guard.
5. **Any number of PLANNED sprints may exist; only one may be ACTIVE** (JFR-189, 2026-10-06) — `createSprint` no longer rejects a second open sprint. The Backlog page lists every open sprint (ACTIVE first, then planned by start date); backlog rows pick a target sprint from a native `<select>`. `startSprint`'s pre-check + the partial unique index remain the only guard, and the Start button is disabled while a sprint is active.
6. **Completing a sprint auto-unassigns non-Done issues** — `completeSprint` looks up the project's DONE-category `ProjectStatus` ids and `updateMany`s the sprint's issues where `statusId notIn` those ids to `sprintId: null`, inside one transaction with the `status: COMPLETED` write. No itemized "here's what will move" dialog — just a plain `ConfirmDialog` ("Complete this sprint?").
7. **Permissions**: `canManageSprint` (PROJECT_LEAD, or a Group-granted `SPRINT_MANAGE` permission) gates create/start/complete. Adding/removing issues to/from a sprint uses the existing `canEditIssues` (PROJECT_LEAD + TEAM_MEMBER, or `ISSUE_EDIT` grant) — it's routine issue editing, not a sprint-lifecycle action. Whenever a new `Permission` enum value is added, `GroupsSettings.tsx`'s `PROJECT_SCOPED_PERMISSIONS`/`ORG_SCOPED_PERMISSIONS` arrays and `PERMISSION_LABELS` map must be updated too — `PERMISSION_LABELS: Record<Permission, string>` is exhaustive, so `tsc` catches a missed one, but the two array lists are not type-checked and are easy to forget.
8. **`moveIssue`/`reorderIssues` sprint-scoping** — see `.context-docs/data-integrity.md`'s `sprintScopeId` bullet. Required for correctness, not optional: without it, dragging on a Sprint-scoped board (which only has the active sprint's issues in client state) would corrupt backlog issues' positions in the shared `(projectId, statusId, position)` column.
9. **Sprint dates are set at creation** (JFR-189) via `CreateSprintDialog`: duration 2w/3w/4w (10/15/20 business days, start day counted, Sat/Sun skipped — Wed the 1st → Tue the 14th) or Custom (free start/end). The server recomputes a preset's end date and rejects a weekend start for presets (`src/lib/sprint-dates.ts`). Dates are calendar days stored at UTC midnight — format with `timeZone: "UTC"`. `startSprint`/`completeSprint` keep a planned start/end and only fall back to "now" when null.
10. **New issues always land in the backlog** (`sprintId: null`) — the issue-creation form was not touched; assignment into a sprint happens only via the Backlog page's "Add to sprint" action.
