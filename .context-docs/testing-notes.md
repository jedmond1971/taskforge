# Testing

- **`src/__tests__/tenancy.test.ts` has a hand-written Prisma mock** — the `mockPrisma` object in the `vi.hoisted()` block lists every Prisma model and method explicitly. When you add a new model that's called from any admin action (or any code covered by that test file), you must add it to the mock or tests fail with `TypeError: Cannot read properties of undefined (reading 'create')`. Add the model with whatever methods it uses, e.g. `adminAuditLog: { create: vi.fn().mockResolvedValue({}) }`. The other test files (`permissions.test.ts`, `docs.test.ts`, etc.) have their own separate mocks — check each one if your new code is exercised by multiple test files.
- **`src/__tests__/docs.test.ts` also hand-mocks `@/lib/s3`** (`deleteObject`, `putObject`, `getPresignedDownloadUrl`, `deleteObjectsWithPrefix`, `getObjectBuffer`) in the same `vi.hoisted()` block. Adding a new S3 helper call to any docs route covered by this file requires adding the corresponding mock function too — an unmocked call resolves to `undefined`, calling it throws `TypeError: ... is not a function`, and the route's catch-all handler turns that into a 500 rather than a clear test failure. Missed on the first pass of JFR-131 (`deleteObjectsWithPrefix` added to the page/section DELETE routes but not to this mock) because `npm test` wasn't run locally before pushing — only CI caught it. `npm test` is now step 3 of the CLAUDE.md pre-commit checklist for exactly this reason.
- **`tenancy.test.ts` also tests admin action *behaviors*, not just the mock structure** — some tests use `.rejects.toThrow(...)` to assert that admin actions throw on invalid input. If you change an action from throwing to returning `{ success: false, error }` (per the Server Action pitfalls pattern), those assertions break. Update them to `const result = await action(...); expect(result).toEqual({ success: false, error: expect.stringContaining("...") })`.
- **Constructing a `NextRequest`/`Request` with a `Buffer`/`Uint8Array` body in a test does NOT auto-populate the `Content-Length` header** (discovered writing `avatar-route.test.ts`, SECH-87, 2026-09-09) — unlike a real browser `fetch()` sending a `Blob`/`ArrayBuffer` over the wire, undici's in-process `Request` constructor leaves `headers.get("content-length")` as `null` for a Buffer body. Any route handler test that exercises a `Content-Length`-based size check must set the header explicitly (`headers: { "content-length": String(body.length) }`) or the check will see it as missing, not oversized. To simulate a genuinely missing header (e.g. testing the "header absent" branch), use a `ReadableStream` body instead, which has no length to infer and needs `duplex: "half"` in the `RequestInit`.
- **React component tests (JFR-134, 2026-08-18)** — `@testing-library/react` and `jsdom` were added as devDependencies for the first component-level test (`src/components/ui/__tests__/rich-text-display.test.tsx`). Use a `// @vitest-environment jsdom` docblock at the top of the file rather than switching the global vitest environment, so plain logic test files keep the faster default `node` environment. `tsconfig.json` sets `"jsx": "preserve"` (Next.js handles that transform itself), which esbuild doesn't understand — without `esbuild: { jsx: "automatic" }` in `vitest.config.ts`, any `.tsx` test fails at runtime with `ReferenceError: React is not defined`. That option is now set globally in `vitest.config.ts` and is safe for all test files (it doesn't touch the Next.js build). When writing a component test that reproduces a callback-identity-sensitive bug (e.g. an effect's dependency array), don't wrap the callback in a fresh inline arrow function in the test's host component — its identity changing every render can mask a bug that only reproduces with a stable callback reference (like a real `useState` setter).
- **DB-backed cross-tenant integration suite (SECH-85, 2026-09-21)** — `npm run test:integration` (`vitest.integration.config.ts`, files `src/integration/*.itest.ts`, deliberately NOT matched by `npm test`, which stays hermetic). It runs against the local Docker Postgres (`taskforge-db` must be up; `.env` is loaded via `loadEnv`) and `src/integration/setup.ts` **refuses to run unless `DATABASE_URL`'s host is localhost** — it creates and deletes rows. `fixtures.ts` `createWorld()` builds two unrelated tenants (Org A / Org B: owners, members, a viewer, projects with issues/comments/attachments/docs, an org API key, OAuth tokens incl. expired/revoked/read-only) with random-tagged unique names and `destroyWorld()` removes everything (verify with `select count(*) from "User" where email like '%@itest.local'` → 0). Only three things are faked: the session (`actAs(user)` / `actAsNobody()` in `session.ts`, mocking `@/lib/auth`), S3 and `next/cache` / `next/navigation`; `permissions.ts`, actions, route handlers and Prisma are real. Every cross-tenant test asserts both "denied" AND "the victim's data is unchanged" (`snapshotA()`), and each includes a control that the same call works for the rightful tenant so a test can't pass vacuously. **When you fix a tenancy bug, add a regression test here and confirm it fails on the old code** (`git stash push -- <fixed files>`, run, `git stash pop`) — that is how the SECH-85 tests were validated. CI runs it as the `integration` job in `.github/workflows/ci.yml` (parallel to `verify`): a `postgres:16` service, `npx prisma migrate deploy` on the empty DB, then `npm run test:integration`; `DATABASE_URL` from the job env overrides any `.env`, and the v1-secret test self-skips because `V1_API_KEY` is unset there. Still run it locally before touching auth, permissions, server actions or API routes, since a CI failure is a slower loop. To rehearse the job locally: `docker run -d -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=taskforge_test -p 5544:5432 postgres:16`, then `DATABASE_URL=postgresql://postgres:postgres@localhost:5544/taskforge_test npx prisma migrate deploy && DATABASE_URL=... npm run test:integration`. MCP tools are exercised through the SDK's `InMemoryTransport` + `Client` against `createMcpServer(ctx)`. Server-action error messages: `moveIssue` wraps every failure as "Failed to move issue — please retry", so assert on that and on unchanged DB state.
- **`authz-matrix.test.ts` (SECH-85)** — statically requires every `route.ts` (with its exact method list, including `export const { GET, POST } = handlers` re-exports) and every exported server action to have a row in `.context-docs/authz-matrix.md`. Adding a route/action without documenting its auth mechanism and tenant scope fails `npm test`.
