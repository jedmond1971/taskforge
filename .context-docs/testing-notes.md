# Testing

- **`src/__tests__/tenancy.test.ts` has a hand-written Prisma mock** — the `mockPrisma` object in the `vi.hoisted()` block lists every Prisma model and method explicitly. When you add a new model that's called from any admin action (or any code covered by that test file), you must add it to the mock or tests fail with `TypeError: Cannot read properties of undefined (reading 'create')`. Add the model with whatever methods it uses, e.g. `adminAuditLog: { create: vi.fn().mockResolvedValue({}) }`. The other test files (`permissions.test.ts`, `docs.test.ts`, etc.) have their own separate mocks — check each one if your new code is exercised by multiple test files.
- **`src/__tests__/docs.test.ts` also hand-mocks `@/lib/s3`** (`deleteObject`, `putObject`, `getPresignedDownloadUrl`, `deleteObjectsWithPrefix`, `getObjectBuffer`) in the same `vi.hoisted()` block. Adding a new S3 helper call to any docs route covered by this file requires adding the corresponding mock function too — an unmocked call resolves to `undefined`, calling it throws `TypeError: ... is not a function`, and the route's catch-all handler turns that into a 500 rather than a clear test failure. Missed on the first pass of JFR-131 (`deleteObjectsWithPrefix` added to the page/section DELETE routes but not to this mock) because `npm test` wasn't run locally before pushing — only CI caught it. `npm test` is now step 3 of the CLAUDE.md pre-commit checklist for exactly this reason.
- **`tenancy.test.ts` also tests admin action *behaviors*, not just the mock structure** — some tests use `.rejects.toThrow(...)` to assert that admin actions throw on invalid input. If you change an action from throwing to returning `{ success: false, error }` (per the Server Action pitfalls pattern), those assertions break. Update them to `const result = await action(...); expect(result).toEqual({ success: false, error: expect.stringContaining("...") })`.
- **Constructing a `NextRequest`/`Request` with a `Buffer`/`Uint8Array` body in a test does NOT auto-populate the `Content-Length` header** (discovered writing `avatar-route.test.ts`, SECH-87, 2026-09-09) — unlike a real browser `fetch()` sending a `Blob`/`ArrayBuffer` over the wire, undici's in-process `Request` constructor leaves `headers.get("content-length")` as `null` for a Buffer body. Any route handler test that exercises a `Content-Length`-based size check must set the header explicitly (`headers: { "content-length": String(body.length) }`) or the check will see it as missing, not oversized. To simulate a genuinely missing header (e.g. testing the "header absent" branch), use a `ReadableStream` body instead, which has no length to infer and needs `duplex: "half"` in the `RequestInit`.
- **React component tests (JFR-134, 2026-08-18)** — `@testing-library/react` and `jsdom` were added as devDependencies for the first component-level test (`src/components/ui/__tests__/rich-text-display.test.tsx`). Use a `// @vitest-environment jsdom` docblock at the top of the file rather than switching the global vitest environment, so plain logic test files keep the faster default `node` environment. `tsconfig.json` sets `"jsx": "preserve"` (Next.js handles that transform itself), which esbuild doesn't understand — without `esbuild: { jsx: "automatic" }` in `vitest.config.ts`, any `.tsx` test fails at runtime with `ReferenceError: React is not defined`. That option is now set globally in `vitest.config.ts` and is safe for all test files (it doesn't touch the Next.js build). When writing a component test that reproduces a callback-identity-sensitive bug (e.g. an effect's dependency array), don't wrap the callback in a fresh inline arrow function in the test's host component — its identity changing every render can mask a bug that only reproduces with a stable callback reference (like a real `useState` setter).
- **DB-backed cross-tenant integration suite (SECH-85, 2026-09-21)** — `npm run test:integration` (`vitest.integration.config.ts`, files `src/integration/*.itest.ts`, deliberately NOT matched by `npm test`, which stays hermetic). It runs against the local Docker Postgres (`taskforge-db` must be up; `.env` is loaded via `loadEnv`) and `src/integration/setup.ts` **refuses to run unless `DATABASE_URL`'s host is localhost** — it creates and deletes rows. `fixtures.ts` `createWorld()` builds two unrelated tenants (Org A / Org B: owners, members, a viewer, projects with issues/comments/attachments/docs, an org API key, OAuth tokens incl. expired/revoked/read-only) with random-tagged unique names and `destroyWorld()` removes everything (verify with `select count(*) from "User" where email like '%@itest.local'` → 0). Only three things are faked: the session (`actAs(user)` / `actAsNobody()` in `session.ts`, mocking `@/lib/auth`), S3 and `next/cache` / `next/navigation`; `permissions.ts`, actions, route handlers and Prisma are real. Every cross-tenant test asserts both "denied" AND "the victim's data is unchanged" (`snapshotA()`), and each includes a control that the same call works for the rightful tenant so a test can't pass vacuously. **When you fix a tenancy bug, add a regression test here and confirm it fails on the old code** (`git stash push -- <fixed files>`, run, `git stash pop`) — that is how the SECH-85 tests were validated. CI runs it as the `integration` job in `.github/workflows/ci.yml` (parallel to `verify`): a `postgres:16` service, `npx prisma migrate deploy` on the empty DB, then `npm run test:integration`; `DATABASE_URL` from the job env overrides any `.env`, and the v1-secret tests supply their own `V1_API_KEY` when none is set (the guard answers 500 if unconfigured, and CI has no `.env` — that is what broke the first CI run). Still run it locally before touching auth, permissions, server actions or API routes, since a CI failure is a slower loop. To rehearse the job locally: `docker run -d -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=taskforge_test -p 5544:5432 postgres:16`, then `DATABASE_URL=postgresql://postgres:postgres@localhost:5544/taskforge_test npx prisma migrate deploy && DATABASE_URL=... npm run test:integration`. MCP tools are exercised through the SDK's `InMemoryTransport` + `Client` against `createMcpServer(ctx)`. Server-action error messages: `moveIssue` wraps every failure as "Failed to move issue — please retry", so assert on that and on unchanged DB state.
- **`authz-matrix.test.ts` (SECH-85)** — statically requires every `route.ts` (with its exact method list, including `export const { GET, POST } = handlers` re-exports) and every exported server action to have a row in `.context-docs/authz-matrix.md`. Adding a route/action without documenting its auth mechanism and tenant scope fails `npm test`.
- **`tenancy.test.ts`'s hand-written `$transaction` mock only implements the callback form** — the `adminRemoveOrgMember` describe block's `beforeEach` sets `mockPrisma.$transaction.mockImplementation((fn) => fn(mockPrisma))`, so any new code under test that calls `prisma.$transaction([p1, p2])` (array form) throws `TypeError: fn is not a function`, not a helpful "missing mock" error. Found adding `revokeOAuthTokensForUser` (SECH-94) — fixed by writing that helper as `prisma.$transaction(async (tx) => { ...await tx.x.updateMany(...); ...})` instead, matching the callback-form convention already used everywhere else in this codebase (e.g. `createIssue`). Prefer callback form for any new multi-write transaction for this reason.
- **`fixtures.ts` `createWorld()` includes a platform-admin fixture user, `w.users.aAdmin`** (SECH-93/94, 2026-09-22) — a member of Org A's project (`TEAM_MEMBER`) whose platform `UserRole` is `ADMIN`, for testing admin-bypass paths (e.g. closed-project write-lock, `adminResetUserPassword`/`adminUpdateUser`/`adminRemoveOrgMember`). Reuse it rather than creating an ad-hoc admin user inline unless the test needs one that isn't a member of Org A's project.
- **Integration tests in one `.itest.ts` file share a single `createWorld()` and leak state between tests** (found SECH-96, 2026-09-22) — e.g. an earlier test in `cross-tenant-actions.itest.ts` leaves a `RELATES_TO` `IssueLink` from `w.A.issue` to `w.A.issue2`, so creating that same link again hits the `(sourceIssueId, targetIssueId, linkType)` unique constraint. For tests that create rows, make throwaway rows (e.g. extra issues keyed `${w.keyA}-9x`) and delete them in a `finally`, and assert counts scoped to those rows rather than to shared fixtures. The world also has **no same-org user who isn't a project member** — create one inline (`User` + `OrgMember` in `w.orgA`) and delete it in `finally` when a test needs that case (as the SECH-95 public-docspace test does).
- **Integration coverage map and extra fakes (SECH-97, 2026-09-22)** — one `.itest.ts` per area, each with its own `createWorld()`: `cross-tenant-actions` (project/org actions), `cross-tenant-routes` (docs incl. file upload, attachments, issues, projects), `token-auth` (external API, v1 secret, OAuth guard, MCP, SECH-94 revocation), `admin-actions` (every export of `admin/actions.ts` × {org OWNER, other-org OWNER, member, anonymous}; a test asserts the list matches the module's exports, so a new admin action fails until it's added), `sprint-actions` (flips both world projects to `workflowMode: SPRINT` in `beforeAll` — in KANBAN every sprint action short-circuits on the mode check before any id scoping is reached), `auth-flows` (invites, consent actions, `/api/oauth/token`, `/api/oauth/register`), `ai-routes`, `search-scoping`. `ai-routes.itest.ts` additionally `vi.mock`s `@anthropic-ai/sdk` (hoisted `create` fn) so it can assert the model is never called for a denied caller and inspect the minted MCP token; it toggles `process.env.AI_CHAT_ENABLED` per test (the flag is read at call time) and restores it in `afterAll`. Server-action `redirect()` is observable because `setup.ts` makes it throw `NEXT_REDIRECT:<url>` — see `redirectOf()` in `auth-flows.itest.ts`. Race conditions are tested with `Promise.all` of 3 identical requests against the real DB (reliably reproduced the refresh-token rotation race).
- **Stored-XSS regression suite (SECH-106, 2026-09-23)** — three pieces, sharing one corpus:
  - `src/test-support/xss-payloads.ts` — 30 payloads (script tags, event handlers, `javascript:`/`data:` URLs, SVG/MathML, iframe/object/embed, style vectors, and the mXSS `<noscript>` and `mglyph`/`<style>` re-parsing chains) plus `activeContentIn(html)`, which returns the labels of any live construct still present. **Nothing in the app imports this file** — it is test support and lives outside `__tests__` only so both suites can reach it.
  - `src/lib/__tests__/xss-corpus.test.ts` — the whole corpus through `sanitizeTipTapHtml` *and* `sanitizeDocxPreviewHtml` (the DOCX allowlist is looser, so it gets its own pass). It also asserts `activeContentIn` fires on the **raw** payloads, so the suite can't pass vacuously through a broken detector.
  - `src/integration/stored-xss.itest.ts` — the same corpus, concatenated into one document, through every persistence path against real Postgres: the four server actions, v1 API (issues + comments, create + update), external API (incl. the plain-text branch of `normalizeBody`, which HTML-escapes rather than sanitises), `/api/issues/[issueId]`, docs page create/update, the `PageRevision` snapshot, and all four MCP write tools. One write per path covers all 30 vectors; per-payload granularity lives in the unit test, since what this half proves is the *wiring*.
- **`rich-text-sinks.test.ts` (SECH-106) is the inventory guard** — a static scan in the style of `authz-matrix.test.ts`, in two halves that only close the loop together: (1) every `prisma.*`/`tx.*` `create|update|upsert` assigning `description`/`body`/`content` must pass through `sanitizeTipTapHtml` or `normalizeBody`, or appear in `EXCEPTIONS` with a written reason; (2) `dangerouslySetInnerHTML` may only appear in `ALLOWED_HTML_SINKS`. An exception in (1) is only defensible because (2) pins where unsanitised data could ever be rendered as markup. **Known limitation:** it matches fields assigned *inline* in the Prisma `data:` object. A value built up beforehand (`data.content = sanitizeTipTapHtml(...)`, as `/api/docs/.../[pageId]/route.ts` and `updateIssue` do) produces no hit at all rather than a false alarm — the integration suite is what covers those. The four current exceptions are the AI-chat transcript (rendered as an escaped React child, never HTML), the two `PageRevision` snapshots (copies of already-sanitised content), and `Project.description` (a plain-text textarea; running an HTML sanitiser over it would delete legitimate angle brackets from prose).
- **`NodeJS.ProcessEnv` cannot be used as the type of an `env` parameter that tests pass plain objects to** — Next augments it to require `NODE_ENV`, so `{ FOO: "1" } as NodeJS.ProcessEnv` fails `tsc` (TS2352) even though vitest runs it. Type such parameters `Record<string, string | undefined>`; `process.env` is still assignable (`AlertEnv` in `src/lib/alerting/config.ts`).
- **`prisma.ts` registers `$on("error")` → `prisma.error` on the shared client in every non-development env, including vitest** — so an integration test can observe it. To prove "this code path must not emit `prisma.error`", run a real failing query through it and also include a control that a failing query on the shared client *does* emit one (a test that only asserts absence can pass vacuously). `alerting-store.itest.ts` is the pattern.
- **Rendered React Email HTML puts `<!-- -->` between adjacent text nodes** (label, colon, value each become a node), so `toContain("Label: value")` fails — assert with a regex that allows `(?:<!-- -->)?`. Also: `vi.spyOn(namespaceImport, "fn")` on an `import * as store` module works for intercepting calls made from another module, which is how the alerting in-flight limit is tested.
